# Learning policies and exceptions

`/policies` is the owner-only policy library. `/assistant` is the integrated questions and decisions queue. Customize Millie and the tool directory link to both. This capability does not require another visible module.

Policies distinguish recurring preferences from facts about one purchase. Supported enforced treatments are expense now, prepaid service coverage, asset/depreciation consideration, refundable deposit, and mandatory personal approval. Advisory guidance can apply to a particular module (for example reimbursement review or budgeting). Merchant rules still handle deterministic category assignment. No policy or template is enabled by migration.

Each policy has an effective purchase-date range, currency, inclusive amount limits, and optional merchant phrase, current category and owned account. Conditions are ANDed. Merchant matching normalizes ASCII letters/numbers and spaces and matches whole phrases; it does not guess brand aliases. Financial policies apply across the category, timing and automatic receipt paths so switching paths cannot evade them. Contradictory matching treatments produce an exception; there is no silent specificity tie-breaker. Guidance cannot override permissions, evidence requirements or hard dollar limits.

The shared pure evaluator in `_shared/learning-policy.ts` handles context, UI preview, validation and planner decisions. Database matching independently enforces the same conditions before automatic writes. Both use the current recorded category, never a model-selected category to expand scope. A receipt can be analyzed and matched even when policy prevents automatic financial approval; the existing manual review path remains available.

`finance_learning_policies` stores current definitions; `finance_learning_history` preserves every saved revision, including pause/resume. `finance_learning_state` fences prepared analysis. There is no delete endpoint. Policy saves do not edit transactions or schedules and do not replay historical approvals. Any later reanalysis still observes ownership, continuity, deduplication, prior user decisions and closed-period checks. Open eligible purchases can be reconsidered once when their applicable policy revision changes.

Saved exception answers remain attached to their original work item and transaction after completion. New analyses load only answers linked to the selected owned purchases. Corrections preserve the old answer in `finance_assistant_history`, reopen the question, and queue a new revision. A prepared financial action is rejected if its answer facts or policy generation have since changed. The user may explicitly turn an answer into a reusable policy through the policy editor; private purchase facts are not silently generalized.

Ask-first policies allow a fully supported proposal but prevent automatic saving. Manual approval is a one-purchase override, not a rewrite of the policy. Timing proposals still need exact coverage dates and owner-confirmed asset assumptions; a policy is not evidence of these facts. An unresolved conflict can be narrowed in the policy editor or handled with manual financial tools. Closed reports and original amounts remain protected in either path.

Execution uses the existing durable worker, request IDs, provider gateway and dollar reservations. New answers and policy changes never increase allowance or trigger paid retries. No model is called to preview policy scope, manage policies, or read the exception queue. Internal worker capabilities can read policies, but cannot create them or expand permissions.

Validation: `tests/learning-policies.mjs` covers scope boundaries, conflicts, evidence checks, receipt gates and planning/replay. `tests/learning-security.sql` uses synthetic users and a rollback to verify ownership, stale writes, explicit overrides, answer history, immutable amounts and held periods. Existing assistant, autopilot, billing, receipt and analyst regressions remain applicable. Deployment requires the learning migration, updated finance-assistant and finance-autopilot functions, then the frontend. No new secrets or cron jobs are needed.
